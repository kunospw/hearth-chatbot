Hearth · Flutter handoff · Relationship Journal

A relationship engine that changes the story, not just a progress bar

Values are owned by the backend, not the model. The model may propose an event; a deterministic engine decides whether it counts, how much, and what the next reply is told. Every change is logged, explainable and reversible.

DeterministicSame inputs give the same outcome. Rules, magnitudes and thresholds live in server tables, not prompts.
AI proposes, backend decidesThe model can name one event kind with evidence. It can never set numbers, stages or facts.
Gradual by designPacing, cooldowns, diminishing returns and scene budgets make slow burn actually slow — and farming useless.
Not romance by defaultAffection ≠ attraction. Romance needs an allowing type and its own signal; stages are per character and scenario.

1 · The loop for every user message

1 · CLIENTUser sends a messageFlutter posts it to the chat edge function. No relationship maths on the device.
→
2 · ENGINE (PRE)Classify the user's actionRule matchers + a small classifier pick at most one event kind from a fixed list.
→
3 · VALIDATEApply safeguardsTrivial filter, cooldown, diminishing returns, scene budget, gates, locks, pacing.
→
4 · PERSISTAppend event, update stateOne transaction: event row + new values + stage. Manual pacing writes a suggestion instead.
→
5 · PROMPTBuild the context blockStage, type, value words, behaviour lines, locked facts — from fresh state.
→
6 · MODELReply + optional proposalThe proposal re-enters step 3 as a candidate for the character's own actions. Never applied directly.

Because step 5 runs after step 4, a meaningful action changes this reply: a promise kept at Trust 31 gets a guarded nod; the same promise at Trust 62 gets a confession about the logbook. The prototype does this with tiered reply pools; production does it with the context block.

2 · Safeguards (validator, in order)

Trivial filterUnder 4 words, out-of-character lines (( … )), emoji-only, or a normalised-text hash seen in the last 20 turns → no event.
Evidence checkA model proposal must quote text that actually appears in the last 6 messages, and its kind must be in the catalogue. Otherwise it is dropped and logged.
CooldownEach event kind fires at most once per 6 user turns per relationship.
Diminishing returns× 1 / (1 + 0.5·n), where n = times this kind counted in the last 30 turns. The fifth “thank you” is worth a third of the first.
Scene budgetTotal movement capped at 8 points per 10 turns, and ±12 per value per day. Excess is scaled down and noted in “why”.
Romance gateAttraction events only apply when type is Romantic or “Let the story decide”. Affection never converts into attraction.
LocksA locked stage never moves automatically. Events tagged as contradicting a locked fact are rejected.
IdempotenceEvents key on (message_id, kind). Rewrites and regenerations never double-count; editing a message re-evaluates and replaces its event.
PacingMultiply last, round to 0.5. Manual pacing writes a suggestion for the user to approve.

Stage names are per relationship (presets: Romance arc, Friendship, Rivalry, Family, or fully custom like Morrow's “Visitor → Keeper of the Stacks”). Setbacks lower values; hysteresis stops one argument from erasing a stage, but a real betrayal can.

5 · Database (Supabase / Postgres)

create table relationships (
  id uuid primary key,
  user_id uuid not null references auth.users,
  character_id uuid not null, universe_id uuid,
  persona_id uuid,                    -- who you play as
  type text not null default 'undecided',
  pacing text not null default 'slow',
  trust numeric(5,1), affection numeric(5,1),
  attraction numeric(5,1), tension numeric(5,1),
  stage_idx int not null default 0,
  stage_locked bool not null default false,
  romantic_from int,                  -- null = no romance stages
  version int not null default 0,     -- optimistic locking
  unique (user_id, character_id, universe_id, persona_id)
);
create table relationship_stages (
  relationship_id uuid, idx int, name text,
  primary key (relationship_id, idx));
create table relationship_events (     -- append-only
  id uuid primary key, relationship_id uuid,
  conversation_id uuid, message_id uuid,
  kind text, source text,  -- engine|model_proposal|user|undo
  deltas jsonb, multipliers jsonb,     -- pace, repeat, cap
  evidence text, why text,
  stage_before int, stage_after int,
  undone_by uuid, created_at timestamptz,
  unique (message_id, kind));
create table relationship_facts (
  id uuid primary key, relationship_id uuid,
  text text, locked bool, tags text[]);
create table relationship_suggestions (
  id uuid primary key, relationship_id uuid,
  event jsonb, status text,   -- pending|applied|dismissed
  created_at timestamptz);
-- RLS: user_id = auth.uid() on every table.
-- Values change only via the apply_event() and
-- apply_correction() SQL functions (security definer).

8 · Edge cases

  • Scope: one relationship per user × character × universe × persona. Different universes never share values; several chats in the same world do.
  • Rewrite / alternate replies: character-side proposals attach to the visible alt; switching alts re-evaluates. User-side events never change.
  • Deleted chat: its events stay in the timeline marked “from a deleted chat”, so the history still adds up. The user can undo them individually.
  • Corrections: write a user event with the diff (source = user). The engine treats it as the new baseline, and the Journal shows it as “Your correction”.
  • Undo: writes a reversing event linked by undone_by. The original is struck through, never deleted.
  • Type change: switching to Platonic or Family freezes attraction for prompts (n/a) and caps romance stages, but keeps history.
  • Concurrency: the version column + apply_event() in one transaction; the client re-fetches on conflict through Supabase realtime.
  • Safety: the content policy still governs the reply; relationship state can never unlock content the account settings don't allow.
